# Ekoa Bridge — installers / distribution

Canonical distribution is **GitHub Releases** on `gongiskhan/ekoa-bridge`. The
`latest/download` URLs always resolve to the newest release:

```
https://github.com/gongiskhan/ekoa-bridge/releases/latest/download/<asset>
```

> **OPEN after the move into `ekoa-code`.** The source now lives here, but the
> release URLs above still point at the `ekoa-bridge` repository, and they are
> baked into `install.sh`, `install.ps1` and every install command the web app
> has ever displayed. Deciding where releases are cut from now is a distribution
> decision, not a code move, so nothing here was repointed: keep publishing the
> assets to `gongiskhan/ekoa-bridge/releases` (the repository can hold releases
> without holding source) until that decision is made. Changing the URLs means
> re-issuing every install command already in circulation, so it should happen
> once, deliberately, with the old release kept as a redirect or a final build.

## Why there are no double-click installers any more

There used to be `Instalar Ponte Ekoa.command` (macOS) and `.bat` (Windows), so a
non-technical user could install without touching a terminal. **They were removed
because they did not work for the user they existed for.**

A `.command` file downloaded from a browser carries the `com.apple.quarantine`
attribute. macOS refuses to run it and offers no "run anyway" in the dialog — the
user has to go to *Definições → Privacidade e Segurança*, scroll to a blocked-item
notice, and click *Abrir mesmo assim*. That is a longer and stranger journey than
pasting one line, and it is exactly the journey a non-technical user cannot be
walked through over the phone. Code-signing and notarisation would remove it, and
the owner declined that (cost + an Apple Developer account), so the honest fix is
to stop shipping a file that gets quarantined.

**A command pasted into a terminal is not quarantined**, because nothing was
downloaded to disk for Gatekeeper to mark. So the supported path is now one
copy-pasteable line per OS, generated by the web app with the right Ekoa address
already in it (see below).

## Artifacts (release assets)

| Asset | Source here | Audience |
|---|---|---|
| `install.sh` | `install.sh` | macOS + Linux — `curl … \| bash -s -- --url <ekoa>` |
| `install.ps1` | `install.ps1` | Windows — `irm … \| iex`-style scriptblock with `-Url <ekoa>` |
| `ekoa-bridge-latest.tgz` | `npm run pack:dist` (stable-named copy) | what both installers fetch; also `npm i -g <url>` |
| `ekoa-bridge-<version>.tgz` | `npm run pack:dist` | versioned archive |

### Why `pack:dist` and not a bare `npm pack`

This package lives in the `ekoa-code` monorepo as `@ekoa/bridge` and depends on `@ekoa/shared` with
the workspace range `*`. That range resolves only inside the monorepo — a laptop running
`npm i -g` would go looking for `@ekoa/shared` on the registry, where it is not published, and the
install would fail. The daemon needs shared's RUNTIME, not only its types (`BridgeFrame` is a zod
schema it parses every frame with; `canonicalTaskBinding` is the function it signs bytes with), so
copying generated types the way `clients/cortex-cli` does would not be enough.

`npm run pack:dist` therefore bundles `@ekoa/shared` into the shipped `dist/cli/index.js` with
esbuild and packs from a staging tree whose manifest is derived from this package.json minus the
workspace dependency. Everything else (playwright, ws, execa, zod, pdfjs-dist, mammoth,
`@vscode/ripgrep`) stays external and installs on the laptop as before. `tsc -b` is untouched and
remains what CI typechecks and what the test suites run against.

Both scripts do the same four things: check Node 20+, install the CLI globally,
pair (device-code flow) and start the bridge. On macOS/Linux "start" means
`ekoa-bridge autostart on` — a per-user LaunchAgent / systemd user unit, so the
bridge survives reboots and the terminal can close (an upgrade also stops a
still-running old daemon first, or launchd would lose the pidfile race to it).
Windows has no autostart yet and falls back to a foreground `serve`. Pass
`--no-start` / `-NoStart` to install without pairing and starting.

## The Ekoa address travels in the command

The old launchers defaulted to `EKOA_CORTEX_URL=http://localhost:4111`. On a user's
machine that points at *their own* laptop, so pairing could never connect — this
was a real failure in the field, not a theoretical one.

The scripts no longer guess. The web app knows its own API origin and bakes it into
the command it displays, so the user copies a line that already contains the right
address. Running a script with no `--url` prints a warning and falls back to the
CLI's own default rather than silently pairing against nothing.

## Cut a release

Run from `clients/bridge/` in an `ekoa-code` checkout.

```bash
# 1) bump the version in package.json AND src/version.ts (test/scaffold.test.ts
#    fails if they disagree — the version travels to Cortex in the `hello` frame,
#    so a drifting constant would make the machine list report the wrong build)
npm run build
npm test
npm run pack:dist                                 # -> ekoa-bridge-<version>.tgz
V=$(node -p "require('./package.json').version")
cp "ekoa-bridge-$V.tgz" ekoa-bridge-latest.tgz    # stable-named copy the installers fetch

# 2) publish the GitHub Release with all assets
gh release create "v$V" --title "v$V" --notes "Ekoa Bridge v$V" \
  "ekoa-bridge-$V.tgz" ekoa-bridge-latest.tgz \
  packaging/install.ps1 packaging/install.sh
```

Re-running for a new version: `gh release create "v$V" …` with the new assets; the
`latest/download/ekoa-bridge-latest.tgz` URL then points at the new build automatically.

## Capabilities and the daemon version

`serve` sends a `hello` frame on every connect advertising `machineName`, the daemon
version, and the capabilities this build implements — `local.filesystem` and
`attended.card_login` by default. Cortex records that list and intersects it with the
org's capability grants before routing anything to the machine.

This matters for upgrades: a machine running a build older than 0.2.0 sends no
`hello`, so Cortex knows it cannot hold an attended ceremony and says so, instead of
opening a ceremony the daemon will silently drop. `extraCapabilities` and
`egressEndpoint` in `config.json` opt a machine into the rest.
